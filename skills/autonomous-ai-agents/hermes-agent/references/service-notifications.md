# Compact service-notification display

## Procedure

1. **Trace provenance before changing rendering.** Inspect the gateway display kind, transcript projection, live queued-input path and existing collapse controls. Preserve the complete gateway notification and model context; this is a presentation change. Prefer explicit `internal_notification` metadata. For legacy/live background-process text without that metadata, require both an anchored process header and the exact internal-origin marker. Ordinary user messages and quoted examples must remain ordinary messages.
2. **Use one projection for restored and live messages.** In the inspected TUI, `domain/messages.ts` and `app/createGatewayEventHandler.ts` use `asServiceNotification` to produce `Msg.kind = 'notification'` with the original text retained. Keep status extraction bounded to the header so output logs cannot supply a misleading exit code. Show success, failure or continuing activity in the summary; retain failure codes when collapsed.
3. **Render the requested row type without extra spacing.** For a disclosure, reuse the native click/state mechanism in `MessageLine`, truncate the closed label to available width, and reveal the sanitized original text on expansion. Align `estimatedMsgHeight` with the closed row so virtualization does not reserve space for hidden logs. Inspect short `kind: 'event'` timeline rows separately from `kind: 'notification'`: a fixed bottom margin on the event branch can leave blank rows even when disclosures already occupy one line. In compact mode, remove that event-row spacer without changing spacious-mode or ordinary-message spacing. Prefer the renderer's local compact-mode margin over a global transcript-layout change.
4. **Exercise behavior at distinct interaction layers.** Test narrow and wide initial layouts, failure and heartbeat labels, restored history, unmarked/quoted user text, and expand/re-collapse. Render consecutive event rows and assert both row count and absence of empty lines in compact mode; retain assertions for spacious mode and surrounding ordinary messages so a global spacing regression cannot pass. Reuse the complete shipped `renderToScreen` root setup, including `FocusManager`. Calling a handler through `reconciler.discreteUpdates` tests state updates at input-event priority; it does not test terminal mouse delivery or coordinate hit-testing. Add a pointer-path check through the native input parser and dispatcher, and verify the actual terminal interaction before claiming that a physical click works. Missing focus setup can unmount a test tree during child removal and masquerade as a layout defect. Inspect renderer errors and tree state before changing product layout to satisfy such an assertion.
5. **Build, activate and observe separately.** Run the relevant Vitest tests and typecheck, then build. Follow the frontend-only execve procedure in `references/themes.md`: guard the exact session, frontend PID, entry point and expected bundle hash with a one-shot marker. Never restart the gateway or another chat. Read back the resumed session, loaded bundle and reset process uptime; then inspect actual notification-row heights through a temporary zero-height widget that records only matching labels and dimensions, not the transcript. Remove diagnostic widgets after verification.
6. **Close with the user-facing outcome and an unambiguous target.** State whether the new display is active and what remains unverified. Explain that the real service row in transcript history is interactive; a copied arrow and placeholder identifier in the assistant's report is plain text. Prefer a location description over a lookalike pseudo-button, and label illustrative text as noninteractive if an example is necessary. Distinguish this UI task from any ongoing substantive task: a package-install notification is not proof of model generation or editing. Keep local application, commit and publication status separate; inspect the current branch and publication guard rather than assuming the checkout is still publishable.

## Diagnose a reported non-working click

1. Establish the clicked target before reading broad mouse-handling code. Check the supplied screenshot or literal label; if it could be the example in the report, ask one short factual question distinguishing the real notification from the example. This clarifies an already-performed action, rather than making the user run a test.
2. Treat an example-only click as a communication error: explain the actual control's location, remove the ambiguity, and stop that investigation. It does not establish a renderer defect or justify changing mouse settings.
3. For a confirmed real-control failure, reproduce through the input path. Inspect the owning frontend's mouse/inline/native settings, hit target, coordinates, clipping and expansion state; do not infer the cause from the absence of a window in one capture. Keep diagnostic capture scoped to labels, dimensions and allowed environment fields.
4. Separate the verdicts: row rendered, handler works, pointer event reaches the control, and physical interaction observed. Do not promote one verdict into another. Remove temporary probes after the investigation.

## Canonical live delivery and verification pitfalls

- Consume the existing `message.start` service card before rendering the subsequent queued-to-started input. `display_kind`, `display_text` and `text` are in the payload; `admission_id` is on the event envelope. Reuse the bubble ledger to prevent the same admission appearing again through pending snapshots or replay. Do not invent a second gateway protocol when the producer already sends this metadata.
- Retain the original body separately from the collapsed title. Handle process and async-delegation completion kinds identically in history and live display. Legacy fallback requires an anchored recognized header plus the internal-origin marker; quoted human text remains ordinary. A delegation payload may carry an appended memory block, which must stay inside the disclosure.
- Display deduplication is not acknowledgement of a background job or suppression of a generated assistant reply. Never claim those stronger guarantees from a one-row renderer test, and never hide substantive assistant results using text heuristics.
- Run TUI tests with `HERMES_TUI_ACTIVE_SESSION_FILE` and `HERMES_TUI_RESUME` unset. Inherited live values can redirect cold-resume fixtures and overwrite the live active-session marker with fixture IDs. If this happens, recover the ID from the running frontend's actual state before restoring the marker; do not trust the overwritten file or a remembered ID alone.
- The installed Ink input path listens to `readable`, not `data`. A bounded native pointer probe can enqueue SGR bytes through `stdin.unshift` only when no user input is pending. Use painted `nodeCache` coordinates, which include scrolling, rather than summing Yoga offsets. Guard a temporary probe by the exact frontend and live session, verify closed/open/closed heights, and remove it afterward. Label synthetic display fixtures as diagnostics, never as real worker results.
- Limit scratch discovery to the necessary directory level; archived source checkouts can multiply an otherwise small recursive search into megabytes of irrelevant output.

## Verification boundary

A recognized backend marker is not proof that the user sees a compact row or that the assistant remains silent. Verify the rendered surface independently. A mounted one-row label proves appearance, not clickability; a direct handler invocation proves state behavior, not mouse delivery. Closing a disclosure must leave its one-line header visible, and opening it must expose the original output. Do not call a source edit or successful build live adoption without checking the running frontend.
