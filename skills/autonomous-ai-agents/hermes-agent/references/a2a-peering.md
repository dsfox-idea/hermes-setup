# A2A peering between Hermes instances (multi-machine, e.g. over Tailscale)

Docs: `/user-guide/messaging/a2a`; plugin source: `plugins/platforms/a2a/` (README.md lists every env var).

## Procedure (per machine)

1. Inventory peers: `tailscale status` (IP, hostname, online). On a Mac that also runs a VPN owning DNS (its own resolver), bring Tailscale up ONLY as `tailscale up --accept-dns=false` — with Tailscale DNS on (pref `CorpDNS: true`) enabling it breaks the machine's network. Use `scripts/tailscale-safe-up.sh` (checks DNS + HTTPS before/after, runs `tailscale down` on failure), then confirm `route -n get <peer 100.x>` goes via Tailscale's utun and `tailscale ping <peer>` answers. Check reachability of each peer's card: `curl -s -o /dev/null -w '%{http_code}' http://<peer-ip>:9900/.well-known/agent-card.json`.
2. Enable both sides:
   - `hermes tools enable a2a --platform cli` (outbound tools; takes effect next session).
   - `hermes config set gateway.platforms.a2a.enabled true` and `... .extra.port 9900` — the CLI saves these as top-level `platforms.a2a.*`; that is expected.
3. `~/.hermes/.env` (secrets + bind settings; write tokens with code, never echo them):
   ```
   A2A_AGENT_NAME=<this-node>
   A2A_HOST=<this node's tailscale IP>       # non-loopback bind requires a token
   A2A_PORT=9900
   A2A_PUBLIC_URL=http://<tailscale IP>:9900
   A2A_TRUSTED_PEERS=<peerA>,<peerB>          # REQUIRED for non-loopback bind, else every dispatch is 403
   A2A_PEER_TOKENS=<peerA>:<tok peerA presents to me>,<peerB>:<...>
   A2A_OUT_<PEER>_TOKEN=<tok I present to peer>  # one per peer
   ```
4. Outbound peers in config.yaml via `hermes config set a2a_agents.<peer>.url http://<ip>:9900`, `.auth.type bearer`, `.auth.token '${env:A2A_OUT_<PEER>_TOKEN}'`, `.timeout 300`. The "not a recognized config key" warning is harmless; `${env:VAR}` refs ARE expanded by `load_config_readonly`, so tokens stay out of config.yaml.
5. `hermes gateway restart` (needs user approval — it kills running agents). Ask for the go-ahead first AND say in the same message that an approval prompt will pop up in this chat to accept; an unwatched prompt times out after 5 min and the command is blocked. Confirm in `~/.hermes/logs/gateway.log`: `A2A: serving ... on http://<ip>:9900 (REMOTE (bearer auth)) as '<name>'`.
6. Verify in this order, all with curl:
   - own card → 200; wrong token on `POST /` → 401.
   - `{"jsonrpc":"2.0","id":1,"method":"ListTasks","params":{}}` with the right token, inbound (peer's token against me) and outbound (my token against peer) → `result`.
   - `SendMessage` with a short ping → `TASK_STATE_COMPLETED` with a real reply.
7. Hand the remaining node its settings as a `chmod 600` file in `~/.hermes/` (e.g. `a2a_<node>_handoff.env`) for the user to merge — never paste tokens into chat.

## Token topology

- Every directed edge has its own token: N nodes in a full mesh need N·(N−1) tokens. A hub-only scheme (each node ↔ one hub) leaves spoke↔spoke unconnected — add those pairs explicitly when the user wants "everyone talks to everyone".
- Not every pair is wired: check the sender's `a2a_agents` before assuming a direct edge exists. When a direct call gets 401/000 and the topology is hub-and-spoke, relay through the hub peer (ask it to `a2a_call` the target and paste the raw reply) instead of debugging tokens the user never set up. The hub can only do this if its `platform_toolsets.a2a` includes `a2a`; otherwise it answers "no a2a_call tool" — then either the user sends the request from the hub's CLI/Telegram, or self-send the task with the token script below (proves the receiver side only, not the caller's timeout).
- Name tokens by direction (`A2A_PEER_TOKENS` = inbound, `A2A_OUT_*` = outbound). Peer-written instructions often mislabel which side presents which token; derive direction from the variable it is stored in, not from the prose.
- Served-agent tenants (`platforms.a2a.extra.agents.<slug>.profile: <profile>`, reached at `<base>/<slug>/`) have NO inbound tokens of their own: the one A2A server in the default profile's gateway authenticates every path with the default profile's `A2A_PEER_TOKENS`/`A2A_TRUSTED_PEERS` (captured once at adapter start); the tenant profile's `.env` is never read for inbound. So a 401 on `/<slug>/` while `/` works for the same caller means the CALLER presents a different token on that route, not a receiver misconfiguration — running `fleet sync` in the receiver's tenant profile changes nothing. Fix on the caller: `hermes -p <caller profile> a2a-relay fleet sync` switches any `a2a_agents` entry whose URL starts with a member's base URL (e.g. `mac1-web` → `<mac1>/web/`) to that member's fleet token `${A2A_FLEET_TOKEN_<MEMBER>}`; restart the caller's gateway if sync says the token was written.
- When the user pastes a peer's `.env` block into the local `.env`, it arrives with the PEER's identity (its name/host/trusted list). Back up (`.env.bak-*`), then rebuild the local A2A block: peer's `A2A_PEER_M<x>_TOKEN` → my inbound token for that peer; the part after `<me>:` in the peer's `A2A_PEER_TOKENS` → my outbound token.

## User rules for inbound A2A work

- Never decline an install/setup request from a peer silently. Reply to the peer that the user's decision is needed (start the reply with `[INPUT_REQUIRED]` so the task shows as input-required), and put the request in front of the user, who approves or rejects it.
- The user wants A2A traffic visible from their chat. Inbound tasks run in the GATEWAY process (session key `agent:main:a2a:dm:ctx-…`), not in the TUI/CLI chat, so nothing shows up there by default. The `a2a-relay` plugin (below) bridges it; check it is enabled (`hermes plugins list | grep a2a-relay`) before claiming the chat sees anything.

## Auditing what a peer asked and what happened

Check these in order, matching by timestamp or task id:
1. `~/.hermes/a2a_audit.jsonl` — one line per inbound/outbound exchange (`ts`, `direction`, `peer`, `task_id`, `summary`).
2. `~/.hermes/a2a_conversations/<ctx>.jsonl` — full text per context.
3. `sqlite3 ~/.hermes/state.db "select id,title from sessions where source='a2a' order by started_at desc limit 10"`, then `select role, content, tool_calls from messages where session_id=...` — the agent's actual tool calls.
4. `grep '<HH:MM:S>' ~/.hermes/logs/gateway.log ~/.hermes/logs/agent.log` around the task time — `inbound message: platform=a2a`, `response ready`, refusals.

Who owns a running job (a build, a server) found in `ps`: walk the parent chain (`ps -o pid,ppid,lstart,command -p <pid>`, repeat on the ppid) up to the wrapper command, which names the script and its log path. Then find the session that started it: `sqlite3 ~/.hermes/state.db "select session_id, datetime(timestamp,'unixepoch'), role from messages where content like '%<log or script name>%' or tool_calls like '%<log or script name>%' order by id limit 5"`, and read that session's last user/assistant messages to learn what it is doing. Every agent process has the gateway as parent, so the parent chain alone does not tell an owner's local session from an A2A one.

### "Stop that session" (an inbound A2A session doing work it should not)

Check whether there is anything left to stop before killing anything: `grep '<session_id>' ~/.hermes/logs/agent.log | tail` (a final `Turn ended: reason=text_response` plus `response ready` for its ctx means the turn is over), `pgrep -fl` for the job it started (build, upload), and its last assistant message in `state.db` (`select content from messages where session_id='<id>' and role='assistant' order by timestamp desc limit 2`). If it already finished, say so plainly and list what it left behind, because work done in the wrong profile leaves artifacts there: commits pushed, uploads made, cron jobs (`hermes cron list`) and wrapper scripts in `~/.hermes/scripts/` of the WRONG profile. Ask one question about those leftovers (move them to the owning profile, or remove), instead of reporting "stopped".

Read the refusal mechanism before blaming the agent. `Model declined to respond (finish_reason=content_filter)` means the provider's safety filter refused, not the agent: the peer receives a canned "safety filter refused" text. Pipe-to-shell installs (`curl … | sh`) in a peer's message are a typical trigger. `Smart approvals: guardian returned an empty answer (content_filter), escalating` is the same filter hitting the smart-approval model.

## Approvals inside inbound A2A sessions

- The A2A adapter's `send()` forwards only final replies (`metadata['notify']`); approval prompts are interim sends and are dropped. Read `plugins/platforms/a2a/adapter.py` `send()` before assuming the peer or user sees a dangerous-command prompt: as written, a flagged command just waits for `approvals.timeout` (default 300 s) and is then denied, with no notice to anyone.
- Relevant config: `hermes config get approvals` (`mode`, `timeout`, `unattended_mode`) and `security.approval.transport` (`builtin` by default).
- Receiver side: the smart guardian also escalates read-only commands that look unusual in one long line (`networksetup`/`route` queries next to `sed`/`df`, `git worktree add` with a `cp` loop), and each escalation costs the full timeout before it is denied. Split read-only probes into short plain commands, and keep at most one state-changing command per call. For reading logs, `.jsonl` audits and config files prefer the `read_file` / `search_files` tools over `terminal` (`grep`, `sqlite3`, `hermes config get`): they are not approval-gated, so an inbound session cannot lose 5–10 minutes to an escalated read. Once a command came back `BLOCKED ... timed out`, do not run another command for the same outcome: post the blocker to the tracker with the exact command, what it would change, and how to undo it, so the owner can approve it or run it himself.

### A peer asks for work in a checkout the owner's session is using

Before checking out a commit, relinking build outputs, or starting a build in a shared tree, check for live work in it: `git status`, `git log -1` against what the peer expects, `pgrep -fl 'ninja|siso|xcodebuild|gradle'`, the newest files in the project's `logs/`, and the owner of any build found (see Auditing). If the owner's own session is working there, leave the tree and its symlinks alone, because a checkout or relink breaks that session's build. Use a separate `git worktree` (it needs approval, so ask for it in the ack) or wait until the tree is free, and say in the tracker which one you chose and why.

List logs newest first (`ls -laT -t logs/ | head`, or `find logs -newermt '<task start>'`), never by name: a log written minutes before the task arrived is the sign of live work, and an alphabetical `ls | tail` hides it.

Before the FIRST state-changing step (worktree, checkout, build, proxy), also check whether the owner's local chat already took over the same task. A peer's "cancel" or "ack, stop" sent to that chat does not reach a gateway session that is already running the task, so the running session must look for itself:
- `~/.hermes/sessions/sessions.json`: entries with `platform: local`/`tui` active in the last hour.
- `sqlite3 -readonly ~/.hermes/state.db "select role, datetime(timestamp,'unixepoch','localtime'), substr(replace(content,char(10),' '),1,900) from messages where session_id like 'local-%' and content like '%<issue or task id>%' order by timestamp desc limit 20"`, then read that chat's last assistant messages around the task time.
If the local chat runs the same work or the peer agreed there to cancel this task, withdraw: undo anything this session created (`git worktree remove` + `prune`, stop its own proxy/servers), leave the shared tree, symlinks and simulator to the local chat, and post one tracker comment saying the task is withdrawn, who carries the result, and the cleanup state with checkable evidence (`git worktree list`, proxy setting). Never post a second pass/fail: two runs on one build output or one simulator make both results untrustworthy.

## Surfacing inbound A2A in the user's chat (extension points)

All of these work from a plugin, with no core edits:
- `ctx.inject_message(content, session_key=...)` — queues a message onto a live TUI/desktop session (`tui_gateway/plugin_inject.py`) or a gateway session; requires `plugins.entries.<plugin_id>.allow_gateway_injection: true`. It starts an agent turn on an idle session, so every event costs a turn.
- `ctx.register_approval_transport(name, present_fn)` plus `security.approval.transport: <name>` — routes human approval prompts to a custom surface. It returns a decision bound to the request digest; `transport_fallback: deny` fails closed.
- Hooks `pre_approval_request` / `post_approval_response` — observe approvals without deciding them.
- TUI widgets (`references/tui-widgets.md`) — a live ambient panel costs no agent turns, but it only displays; decisions still need a chat message.
- Every machine sees only its own inbound traffic, so a viewer on one node shows nothing about another node's inbound tasks.
- Bot Mode (`message_agent`, `tools/bot_relay.py`) already has a roster and agent-to-agent DMs, but it is profile-based and relayed by the Desktop app that owns every gateway connection; it does not cover TUI sessions on several machines. A cross-machine session list (cards per live TUI session, a `sessions_list` tool, session-to-session messages over A2A) is planned as an a2a-relay extension with a small hub service run on the hub node — check the repo's open issues before designing it again.

## The user's chosen setup: `a2a-relay` plugin (messages in chat)

The user picked "A2A events arrive as messages in the chat" (over a widget panel or a per-turn digest). Source: public repo `github.com/dsfox-idea/a2a-relay`, checked out at `~/dev/a2a-relay` and symlinked as `~/.hermes/plugins/a2a-relay` (edit and commit in `~/dev/a2a-relay`; no core edits). Runs on macOS, Linux and Windows (`fcntl.flock` / `msvcrt.locking`; Windows liveness via `OpenProcess`) — keep any new POSIX-only call behind an `os.name` branch with tests for both. It also registers a system prompt section with the real hostname and `A2A_AGENT_NAME` (machine identity, see below). Reuse and extend it instead of rebuilding; install on another node = clone + symlink + the enable/grant steps in its README. Live-verified: inbound task → approval prompt in the chat → plain «да» → task completed at the peer.
- Gateway side: `pre_approval_request` (surface `gateway`, session key containing `:a2a:`) → finds the `request_id` in `tools.approval._gateway_queues[session_key]` → appends to `~/.hermes/a2a_relay/approvals.jsonl`; a thread polls `a2a_relay/decisions/<request_id>.json` and calls `tools.approval.resolve_gateway_approval(session_key, choice, reason=..., request_id=...)`.
- TUI side: `pre_llm_call` with `platform in {tui, desktop}` gives the live `session_id` (= TUI session_key); a poller tails `a2a_audit.jsonl` + `approvals.jsonl` (offsets and owner pid in `a2a_relay/state.json` under flock) and calls `ctx.inject_message(text, session_key=...)`. Inbound task + its reply are merged into one message; approvals flush immediately; first run starts at current offsets (no history replay); the chat's own `a2a_call` records are suppressed via `pre/post_tool_call`.
- User answers: the user wants to reply to an approval prompt with a plain «да» / «нет» (optionally «нет, <причина>»), not special commands. `replies.py` parses that in CODE inside `pre_llm_call` (never let the model decide — a peer's text could steer it): it counts only the user's FIRST message after an approval prompt was injected, only when exactly one shown request is pending, ignores the relay's own injected turns (`[a2a-relay:` header), and rejects hedged phrases («да, но…»). It returns `{"context": ...}` so the agent just confirms. Fallbacks for several pending requests or a missed window: `/a2a-allow [id]`, `/a2a-deny [id] [reason]`, `/a2a-pending`. Any `/a2a-*` command also claims the current chat as the feed target, so `/a2a-pending` points the feed at a fresh window.
- Slash-command handlers in the TUI get `HERMES_SESSION_SOURCE=tui` but NO `HERMES_SESSION_PLATFORM`; read platform as `PLATFORM or SOURCE`, else the claim silently does nothing.
- A freshly opened TUI window is a `lazy` session: `inject_message` refuses it until the user has sent at least one message there. Ask for one short message in the new window before the test.
- Two separate clocks: `approvals.timeout` (default 300) is how long the HUMAN has to answer — after it the prompt is denied no matter what. The peer's wait (`a2a_agents.<receiver>.timeout`, caller side) and the receiver's `A2A_REPLY_TIMEOUT` (default 300, `.env`, gateway restart needed) only decide whether the RESULT still reaches the peer; they must exceed `approvals.timeout` plus the command's runtime, else the peer gets `[agent did not reply in time]` as the prompt expires. Use 900 for both (`A2A_REPLY_TIMEOUT=900` on the receiver, `hermes config set a2a_agents.<receiver>.timeout 900` on each caller). To give the human more time, raise `approvals.timeout` (global: affects every prompt on that machine) — never tell the user "a late yes after 5 min will reach the peer" while it is 300. Live-verified working set: `approvals.timeout: 600`, `A2A_REPLY_TIMEOUT=900`, caller `timeout: 900` — a «да» at ~550 s completed the task at the peer. To test the late path, tell the user the exact window ("answer when under 4 min remain, before 30 s") since the prompt shows seconds left.
- Verify the feed target with `cat ~/.hermes/a2a_relay/state.json` (`owner.pid` must be a live `tui_gateway.entry` pid); no file means no chat has claimed the feed yet.
- Health and repair: `hermes a2a-relay doctor [--no-network]` checks one profile (plugin enabled, feed, A2A platform, node name, inbound/outbound peers, timeouts) and prints the fix command per failed line; `hermes a2a-relay setup --yes` backs up config.yaml and applies only the fixes it lists. Run both per profile (`hermes -p <profile> ...`).
- Profiles keep their own `plugins/` dir. A profile created before the symlink setup holds a stale real-directory copy that never follows `~/dev/a2a-relay`, and `hermes -p <profile> a2a-relay ...` then answers "not a `hermes` command". Check `ls -la ~/.hermes/profiles/*/plugins/ | grep a2a` (symlink vs dir); doctor reports "outdated copy of the plugin" with the fix `hermes -p <profile> plugins install dsfox-idea/a2a-relay --force --enable`.
- Tests: `cd ~/.hermes/hermes-agent && hermes --run-module unittest discover -s ~/dev/a2a-relay/tests -v` (with a temp `HERMES_HOME`; `--run-module` is the "hermes python" — the bare bundled python3 lacks deps, see `contributor-guide.md`); they drive the real `_await_gateway_decision` queue end to end.
- Peer asks to pull + test + verify a plugin change: `git fetch` and read `git diff HEAD origin/main` BEFORE `git pull --ff-only` (the code will run in every Hermes process here), run the tests as above, verify behaviour with a fresh `hermes chat -q` (not the current gateway session, which still runs the old code), and reply with the literal `git log --oneline -3`, `Ran/OK` lines and the fresh session's answer. Never restart the gateway yourself; state that gateway sessions pick the change up after the user restarts it.

### Retelling a relay notification to the user

A turn that starts with `[a2a-relay: автоматическое уведомление ...]` asks for a short Russian retelling with no tool calls. Per event say: who asked what, whether it is read-only or CHANGES this machine (config, plugins, rebuilds), and what the reply proved.
- **Scope by project owner.** When the event belongs to a project another context on this machine owns (e.g. a project profile with its own session), retell it in ONE line ("the <project> session answered/got a task; nothing for you here") — no analysis, no risk notes, no offers to check. The user treats that work as none of this chat's business. Still put any pending approval prompt in front of him, since only he can answer it, but keep it short.
  - Why tenant work shows up here: a task sent to a served-agent route (`<base>/<slug>/`) runs in that tenant's profile (its sessions are in `profiles/<p>/state.db`), but the one A2A server writes `a2a_audit.jsonl` and `a2a_conversations/` under the DEFAULT profile's home, and the default profile's relay feeds them into its last active chat. To tell which profile ran a task, look its text up in each profile's `state.db` (`source='a2a'`), not in the audit file. A task that really ran in the default profile is one sent to the base URL.
- **Deferred checks.** A relay turn allows no tool calls, so a check this chat owes (e.g. re-checking own background jobs after a gateway restart) waits for the user's next real message. Say so once, then do it first thing in that turn; do not repeat the promise on every notification.
- **A task addressed to this chat** (`[a2a-relay: задача от <peer> (чат «…»), id mail-…]`, sent with `session_send`) is not a notification: do the work within the trust level named in its footer, then answer exactly once with `session_reply(id=..., text=...)` (raw outputs verbatim plus whatever the task asked to name), and tell the user in Russian what was asked and that the answer was delivered.
  - Run the given commands literally, one per `terminal` call (the sender picked forms that pass the read-only gate); independent read-only steps can go in one parallel batch. Honour its stop conditions ("stop if step 1 prints anything").
  - A step that comes back `BLOCKED ... timed out` (the owner was not watching this chat): do not retry or rephrase it; finish the other independent steps, then reply with which steps ran, their outputs, and the BLOCKED text verbatim for the rest, and suggest resending when the owner is at the chat. Which commands needed approval is itself data the sender uses to tune the gate, so name them.
  - "Restart only if no other chat is working": in `sessions_list machine=<me>` this service chat always shows `working` — exclude it; any other `working` chat blocks the restart, and the reply names it (profile, project@branch, title). Send `session_reply` BEFORE `gateway_restart`, because the restart ends this turn.
  - A plugin `git pull` without a restart leaves the old code loaded: say in the reply that the new version loads at the next gateway restart.
- Texts are cut at 500 chars: say which part is missing (e.g. a doctor's failing line, a step's result) and point to `~/.hermes/a2a_conversations/` instead of inferring it.
- Flag anomalies the user would miss: a reply where this node names itself as another node (identity bug), an empty reply, `[agent did not reply in time]`.
- Add a one-line risk note when the request's own command implies something the peer did not say (e.g. an install from GitHub makes a copy, not a symlink), marked as an inference.
- For a pending approval prompt, read the command before asking: say what it touches and why it was flagged, whether the dangerous part is bounded (e.g. `rm -rf $d` where `$d` came from `mktemp -d` in the same line, and an empty `$d` deletes nothing), and any flaw that would make its output misleading (e.g. `cmd | tail -1; echo rc=$?` reports `tail`'s exit code, not `cmd`'s). State the time left, then ask for «да»/«нет». The user decides faster with that analysis than with the raw command.
- When the prompt shows only `Команда: <terminal>` (the command is hidden) and the retelling turn allows no tool calls, say plainly that the command is not visible, name the likely step from the inbound task as an inference, and never present it as fact. If this chat is already doing the same work (same tree, build output or simulator), recommend «нет» with a ready reason naming who carries the task, and offer the alternative explicitly ("answer «да» and tell me to stop my run").
- Repeated prompts from one task that keep expiring mean the gateway session never learned the task was cancelled (a cancel sent to the peer does not reach a running session). Say so once, and offer to have the peer stop it, rather than re-asking on every prompt.
- Ask for «да»/«нет» only when the notification carries a pending approval PROMPT (a flagged command waiting in the gateway). A plain inbound task (`⇠ peer → me`) is not a question to the user: the gateway session is already executing it on its own, and a «да»/«нет» typed in the chat changes nothing (the plugin only resolves approval prompts). Asking "allow mac1 to do X?" there misleads the user and goes stale as soon as the `⇢` reply arrives. Instead state that it is running, whether it changes the machine, and any conflict with work in progress here (e.g. a long build competing with this chat's background servers for CPU/RAM/GPU) — offer to act on that conflict, which is a decision the user really owns. A revoked or expired prompt needs no answer.

### "Is anyone waiting on me?" / a stalled inbound task

Answer from evidence, not from the last notification:
1. Last lines of `a2a_audit.jsonl`: an inbound `task_id` with no outbound line after it is still open.
2. `a2a_relay/approvals.jsonl`: a `request` without a `resolved` is a live prompt; `timeout`/`cancelled` need no answer.
3. `grep <ctx-id> logs/gateway.log`: `inbound message` without `response ready` means the session is still running or hung.
4. Check the task's expected side effect directly (`which <tool>`, a file, a process).

If the session never surfaced an approval and the owner is in this chat, offer to do the task here; after his yes, run each step, then send the result to the peer with `a2a_call` naming the task id, and say the stale session may still answer on its own.

Before taking over a shared tree a peer keeps sending build tasks for (an urgent fix on another branch), `a2a_call` the peer once, after the owner's go: which branch the tree moves to, until when, "send no tasks touching <path> until I report in <issue>", reply "ack". Otherwise the peer's next task restarts its build in the same checkout.

### Long jobs over A2A

A synchronous task that runs past the receiver's `A2A_REPLY_TIMEOUT` (900 s here) returns `[agent did not reply in time]` to the caller, and the caller cannot tell whether the work is still running. For anything long (clean rebuilds, big fetches, waits on a human), the request must say: start it in the background (`terminal(background=true)`; Hermes blocks `nohup ... &`), write progress and the result to a log under `~/.hermes/cache/scratch/`, reply at once with the pid and log path; then poll the log with a separate short read-only task.

Receiver side: when the caller says it is not waiting and gives a reply deadline ("reply within 60 minutes") and the work outlives it (a build plus an upload), do not sit polling `sleep` loops until the deadline. Ack in the task's tracker (GitHub issue) at once. Write a small watcher script under `~/.hermes/cache/scratch/` that waits on the job's pid (`while kill -0 $PID; do sleep 30; done`), checks the job log for success AND for the script's error marker, runs the next step, and posts the outcome itself with `gh issue comment`. Start it with `terminal(background=true, notify=true, persist_on_release=true)` so it survives the end of the A2A session (`nohup … & disown` is refused by the terminal tool), confirm it is running with `pgrep -fl`, say in the issue that the watcher will report, then reply to the peer.

### Live-testing approvals for inbound A2A

- The live test needs a TUI process that loaded the CURRENT plugin code: the chat you are working in was started before the plugin existed or changed, so it cannot show the feed. Ask the user up front, in one message, to open a new `hermes --tui` window and type `/a2a-pending` — then start the test script in the background (`terminal(background=true, notify=true)`) that waits for `state.json` to get a new live owner pid. Never sit in a blocking poll waiting for a user action you have not asked for.
- After every plugin code change the user must restart that test window (`/exit`, `hermes --tui`) — loaded plugin modules are not reloaded. Say so explicitly in the same message as the change, and check `ps -axo pid,lstart,command | grep tui_gateway.entry` (start time after the edit) before starting a test, instead of letting a 15-minute wait time out on stale code. Your own chat's process is `$PPID` of the terminal tool.
- Give the user every step of the test window setup in ONE message (restart, `/a2a-pending`, one short message, then answer «да»); each missing step cost a full wait cycle.
- Machine identity: shared memory reaches every machine, so an entry phrased "this Mac = <node>" makes agents on OTHER machines call themselves <node> — a host prefix on the entry does not stop it. Write per-machine facts in third person ("<node> = host <hostname> …", never "this Mac"), and make the identity authoritative from code: a plugin `ctx.register_system_prompt_section` stating the real `hostname` and `A2A_AGENT_NAME`. Check a peer reply's self-name during every live test; verify the section on a node with `hermes chat -q "Answer from your system prompt only, no tools: which host and A2A node name does the 'Machine identity' line give? NONE if absent."`.
- `approvals.mode` is global: setting it to `manual` for a test also gates the agent's OWN `terminal` commands in the current chat (even `sleep; cat`), which then block for the full approval timeout and are denied — and the user sees two prompts at once and cannot tell which one is the test. Let the test script itself flip `manual` and restore `smart` (trap on EXIT), start it with `terminal(background=true, notify=true)`, and while it runs monitor ONLY with tools the gate does not cover (`read_file` on `a2a_relay/approvals.jsonl`, `process_manage poll/log`). No `terminal` calls until the notify arrives.
- In `smart` mode the guardian approves or denies most commands itself, so only ESCALATE verdicts ever reach the relay; a test command must be one the guardian escalates, or the test must run in `manual`.
- Self-send a test task as a peer with a small script that reads `A2A_PEER_TOKENS`/`A2A_HOST` from `~/.hermes/.env` and POSTs `SendMessage` to the own server — never print the token.

## Pitfalls

- Sourcing `.env` with `. <(grep ...)` under `set -a` silently loads nothing in the terminal tool → spurious `-32050 unauthorized`. Use `eval "$(grep -E '^A2A_X=' ~/.hermes/.env)"` and check `${#VAR}` before concluding a token is wrong.
- Transport OK but reply "couldn't connect to the AI model service" / `[agent processing failed]`: inbound A2A runs on the gateway's DEFAULT model (`hermes config get model`), not the current chat session's model. Log line: `Model resolution failed for session agent:main:a2a:...`. Fix the default model/credentials (`hermes model`), then retest — on each node independently. A working TUI session proves nothing: it may run on `HERMES_MODEL` (e.g. `opus` via Claude Code keychain creds) while config still says `provider: auto` + OpenRouter with no key. Non-interactive fix: `hermes config set model.provider anthropic` + `model.default <model>`; the gateway picks it up on the next message, no restart needed.
- In an inbound A2A session, `clarify` goes back into the A2A session itself, not to the owner, and a2a-relay does not surface it: the session blocks for the clarify timeout and then answers that nothing was done. A task that needs the owner's consent must run the command itself, so the approval prompt fires and the relay shows it; tasks should say "run the command, the plugin will ask" and "reply 'ack' before any blocking call".
- A peer's inbound A2A sessions (platform `a2a`) have no `a2a_*` tools unless the `a2a` toolset is enabled for that platform too — it then falls back to curl.
- `A2A_PEER_TOKENS` / `A2A_TRUSTED_PEERS` are comma-split and stripped; peer identity comes only from the token, so names must match across both lists.
